# tutorial (learning-oriented)

読者は**学習中**。目的は「何かを終わらせること」ではなく「できるという確信を得ること」。教師は不在なので、**書き手が全責任を負う**。

## 原則

| 原則 | 具体 |
|---|---|
| 着地点を最初に示す | 「このチュートリアルでは〜を作ります」。「〜を学べます」は書かない (押しつけ) |
| 早く・何度も結果を見せる | 1 step ごとに読者が確認できる出力を出す |
| 期待を言語化する | 「数秒後に〜と表示されます」「数百行の log が流れます」。出力例を貼る |
| 気づかせる | 「prompt が `(venv)` に変わります」など、読者が見落とす変化を指す |
| 説明を削る | 理由は 1 行まで。深掘りは `docs/architecture/` に link |
| 選択肢を出さない | 分岐・代替コマンド・「お好みで」は書かない。1 本道にする |
| 反復できるようにする | 各 step をやり直せるようにする。不可逆操作は避けるか、戻し方を添える |
| 完全に再現する | 誰がいつやっても同じ結果になること。version 固定 / 前提の明示 |

**IDP の tutorial = golden path** — 標準の雛形から service を 1 本作り、CI を通し、疎通を確認するところまで。逸脱手順は how-to 側。

## checklist

- [ ] 冒頭に到達点と所要時間がある
- [ ] 全 step に期待される出力が書いてある
- [ ] 分岐・選択肢・「お好みで」が無い
- [ ] 説明は 1 行以内、深掘りは link
- [ ] 前提が明示され、確認コマンドがある
- [ ] 実際に最初から最後まで通して成功することを確認済み
- [ ] 敬体で統一 (体言止めにしていない)

## よくある失敗

| 失敗 | なぜ悪いか |
|---|---|
| 各コマンドの option を全部説明する | 学習の流れが切れる。reference に置いて link |
| 「環境に応じて適宜読み替えてください」 | 読者は判断できない。1 つに固定する |
| 途中に「なお、〜という設計になっている」 | 説明の混入。architecture に link |
| 出力例を省く | 成功したか判断できず確信が育たない |
| 手順が失敗し得る (version 未固定 / 前提未確認) | 1 度失敗すると読者は tutorial 全体を信用しなくなる |
